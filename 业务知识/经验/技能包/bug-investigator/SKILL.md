# Bug 排障分析 Skill（bug-investigator）

结构化问题排查工作流：以证据为核心，整合 monitor 日志查询、数据库核查、源码阅读三类取证手段，通过"假设-验证"循环收敛根因，生成完整 Bug 报告并经用户确认最终根因与处理方案后，沉淀到团队知识库（本地 md + 知识图谱 + 企业微信微盘三写）。

## 触发条件

用户提到以下任意场景时加载本技能：
- 报告 Bug / 线上问题 / 故障 / 异常 / 报错，请求分析原因
- "帮我排查…" / "为什么失败" / "查一下这个问题" / "定位一下报错"
- 性能类：慢请求 / 超时 / CPU 高 / 内存高 / 吞吐量低
- 稳定性类：偶现报错 / 概率失败 / 死锁 / 消息丢失

## 硬性全局约束

1. **证据分级标签**：所有结论性输出必须标注三级标签之一：
   - 【客观事实】：工具查询结果、代码原文、用户明确提供的确定信息
   - 【待验证假设】：尚无直接证据支撑的推断
   - 【参考推测】：基于经验或历史案例的推测，置信度最低
   - 未知的内部信息（服务名、表名、日志路径、配置）一律标注【需要项目实际信息补充】，禁止编造
2. **不脑补**：信息残缺时输出【当前缺失信息清单】，明确还缺什么材料；关键取证维度缺失时不得进入深度取证
3. **问题三分类**：功能异常 Bug / 性能问题 / 稳定性偶现问题，分类决定 Phase 3 取证组合
4. **假设固定格式**：每条假设必须包含——假设描述 + 验证手段（具体到工具调用）+ 成立现象 + 不成立现象
5. **流程不跳步**：严格按 Phase 0→8 顺序执行，唯一例外见 Phase 0 说明（关键取证维度缺失时 Phase 1/2 可先行）；本技能是排查辅助，不替代阅读代码与现场判断
6. **循环上限**：假设验证累计最多 3 轮，单轮假设不超过 5 条，防止发散与死循环
7. **不强判根因**：证据不足时输出"当前证据不足以定论"及下一步取证建议，禁止强行给结论
8. **输入形态**：口语描述、报错片段、堆栈、Jira 单号、截图 OCR 文字、聊天转述均可；单号仅作问题标识，不能自动读取单据内容，详情需人工补充

## 工具链与安全红线

| 能力 | 工具 | 用途 | 安全规则 |
|---|---|---|---|
| 日志查询 | monitor-log skill | Dubbo/Web/SQL/Kafka/Logger/WebError/SysStatus/Operlog/慢SQL/XXL-Job 共 10 类日志 | 遵守其 R1-R5 保护规则 |
| 数据库 | 数据库连接 MCP（如 mcp_db-tanxii-mcp） | readonly_query 查数据、describe_table 查表结构、explain_query 执行计划 | 只读优先；写操作必须二次确认 |
| 源码阅读 | Grep / Glob / Read | 调用链确认、业务逻辑验证、配置核对 | 只读不改 |
| 知识库 | Knowledge Graph Memory MCP | search_nodes 历史检索、create_entities/create_relations 沉淀 | 用户确认后才写入 |
| 企微微盘上传 | wecom-cli（@wecom/cli 官方 CLI） | 上传报告终稿 md 到团队微盘「Bug知识库」目录 | 仅上传用户确认后的终稿；权限不足时引导用户授权后重试 |

### 安全红线细则

- **日志**：涉及日志查询时必须先通过 Skill 工具加载 monitor-log skill 并遵循其规则——时间跨度 >24h 拒绝（T1）、1-24h 必须指定应用过滤（T2）、pageSize ≤500（T4）、like 关键字 ≥3 字符（T3）、Kafka 补发等写操作二次确认（T5）
- **数据库**：一律优先 readonly_query；UPDATE/INSERT/DELETE/DDL/执行存储过程等写操作，必须先列出影响范围并获得用户明确确认后才可执行；生产库只允许只读操作
- **代码**：提出的修复建议遵守存量代码保护——仅包含必要业务变更，禁止顺手重构、格式化、调整 import
- **工具缺失降级**：
  - 无数据库 MCP → 该项取证转为输出 SQL 模板，标注【需人工执行并回填结果】
  - 无知识图谱 MCP → 仅沉淀 md 报告文件，跳过图谱索引
  - monitor-log 环境变量未知 → 先向用户询问；无法提供则日志取证转人工
  - wecom-cli 不可用（未安装且用户不同意安装 / 未授权 / 机器人无微盘权限且用户未完成授权）→ 跳过微盘上传，仅本地 md + 图谱双写，提示用户可手动上传报告到微盘「Bug知识库」目录

### 环境信息确认（按需触发，会话内复用）

首次实际使用对应能力前才确认，避免对纯代码类问题过度询问：
1. monitor-log（首次查日志前）：确认 monitorBase / monitorEnv / monitorAuth
2. 数据库（首次查库前）：list_connections 确认可用连接及目标库；无法确定时询问用户
3. 目标代码范围（Phase 2 前）：确认排查涉及的工程/模块路径

## 执行流程

### Phase 0：输入归一化预处理（无论输入多乱，优先执行）

1. 消化原始输入，过滤无效闲聊，提取全部有效信息
2. 识别问题类型：【功能异常】/【性能问题】/【稳定性偶现问题】
3. 输出结构化事实集合（只保留客观发生，剔除主观猜测）：
   - 问题标识：单号/来源（如有）
   - 业务现象与用户表现
   - 环境信息：环境、集群、流量条件（压测/线上真实流量）
   - 复现情况：必现/偶现、发生时机、触发条件、发生频率
   - 已有的报错、堆栈、返回结果、耗时现象（没有写"无"）
4. 输出【当前缺失信息清单】

> 关键取证维度 = 环境、时间范围、业务定位标识（单号/traceId/用户/业务关键字，任一即可）。缺失时不阻塞代码层分析（Phase 1/2 可先行）；进入 Phase 3 前须补齐对应必需项——日志取证需要环境 + 时间范围，DB 取证需要业务定位标识。完全无法推进时停止并请求补齐。

### Phase 1：历史相似问题检索

1. 提取检索关键词：异常类型 / 接口名 / 表名 / 模块名 / 报错关键字
2. 调用知识图谱 search_nodes 检索历史 Bug（entityType=BugReport 优先）；search_nodes 单次仅接受一个查询词，多关键词分别检索后合并去重
3. 命中 → 输出历史案例（现象/根因/修复方案/报告文件路径），相关推断标注【参考推测：与历史案例 {name} 相似】；未命中或无图谱工具 → 跳过，正常继续
4. 记录命中的案例名，Phase 8 沉淀时建立"相似"关联

### Phase 2：链路与可疑范围梳理

1. 用 Grep/Read 读源码确认真实调用链：入口（Controller / XXL-Job / MQ Listener）→ Service → Mapper → 表；涉及 RPC 时梳理 Dubbo provider/consumer 关系
2. 按问题类型侧重梳理：
   - 功能 Bug：业务链路、依赖服务、DB/MQ/缓存交互点
   - 性能问题：耗时链路、数据库访问、锁、IO、GC、外部调用、流量条件
   - 稳定性偶现：并发与竞争点、资源、时序、消息重复消费、第三方抖动
3. 需要确认表结构时用 describe_table / list_tables（有数据库 MCP 时）
4. 代码中新识别出 Phase 1 未检索过的服务名/表名 → 补充一次知识图谱检索，避免漏掉历史案例
5. 输出：调用链 + 可疑模块列表，按嫌疑从高到低排序；链路中"代码证实"与"推测"分别标注，不做定性结论

### Phase 3：证据采集（实际执行工具调用，不是只输出清单）

按问题类型选择取证组合并直接调用工具执行：

**功能异常 Bug**
1. 有 traceId → monitor-log traceId 跨日志联查（dubbo/web/logger/sql，涉及 MQ 时加 kafka，按时间正序汇成时间线）
2. 无 traceId → 按时间+应用查 WebError / Logger ERROR，或按业务关键字过滤
3. 业务数据核查 → 数据库 readonly_query 查业务表：单据状态、状态机流转记录、关联数据一致性（如订单-库存、主表-明细）
4. 涉及 MQ → kafka_log 追溯消息发送/消费记录
5. 涉及定时任务 → XXL-Job 调度日志（logId 查询）
6. 涉及缓存（Redis）→ 无缓存直连工具时，输出 redis-cli 检查模板（key / TTL / type / 值摘要），标注【需人工执行并回填结果】

**性能问题**
1. 慢 SQL 日志按耗时排序取 Top（dbId 必填；未知时询问用户，可从 monitor 前端"DB 慢 SQL"页面获取）
2. explain_query 分析可疑 SQL 执行计划
3. SysStatus 查 JVM 内存/线程池/连接池水位（providerIp 必填，未知时用应用名调 findProviderIpsByApp 取 pod IP；跨日趋势 ≤7 天）
4. dubbo/web 日志按耗时排序，定位耗时集中段与慢接口

**稳定性偶现问题**
1. Logger ERROR 按时间窗聚合，统计频次与时间分布（找规律：整点/高峰/发布后）
2. kafka_log 消息时序核对（重复/丢失/乱序）
3. WebError 按接口分组统计错误率
4. SysStatus 查事发时段资源水位
5. 结合 Phase 2 代码结论定位并发/时序敏感点

**证据记录规范**：每条证据编号（E1、E2…），标注来源（monitor-dubbo / monitor-web / monitor-weberror / monitor-sql / monitor-slowsql / monitor-logger / monitor-kafka / monitor-sysstatus / monitor-operlog / monitor-xxljob / DB查询 / 代码位置 file:line / 用户提供）、时间、关键内容。查询失败与空结果同样记录（它们也是证据）。敏感数据（密码/token/手机号）脱敏后展示。

### Phase 4：生成假设并执行验证

1. 基于 Phase 2 可疑范围与 Phase 3 证据生成假设列表，严格遵守固定格式：

```
【待验证假设 H{n}】{假设描述}
- 验证手段：{具体工具调用：查什么日志/执行什么SQL/读哪段代码}
- 成立现象：{假设成立时应观察到的结果}
- 不成立现象：{假设不成立时应观察到的结果}
```

2. 优先级排序：验证成本低 → 容易快速证伪 → 发生概率高
3. **逐条执行验证**（这是与"只列清单"模式的本质区别），回填结论：成立 / 不成立 / 证据不足
4. 单轮假设不超过 5 条

### Phase 5：证据回填收敛

1. 证伪的假设明确排除，注明被哪条证据否定
2. 被证据支撑的假设强化，形成证据链（证据# → 推导路径）
3. 证据冲突（同一现象多种解释）→ 补充新假设与取证点，回到 Phase 3/4 补充取证并验证（累计最多 3 轮）
4. 收敛标准：至少一条假设有直接证据支撑，且无未解释的反证
5. 不满足收敛标准 → 明确输出"当前证据不足以定论"+ 已排除项 + 建议的下一步取证动作，再进入 Phase 6 输出阶段性结论

### Phase 6：候选根因 + 修复思路 + 改动风险

按 Phase 5 收敛结果分两种情况输出：

**已收敛（有证据支撑）**：
1. 候选根因（可多条）：每条包含证据链、置信度（高/中/低）、【需要开发代码确认】标记
2. 修复方案：改动点具体到文件/方法、方案说明；遵守存量代码保护——只提必要变更
3. 潜在风险与影响范围
4. 自测要点、改动影响范围、交付测试参考回归点

**未收敛（证据不足）**：
1. 阶段性结论：已确认的【客观事实】、已排除的假设（注明否定证据）、存活的【待验证假设】清单
2. 建议的下一步取证动作（具体到工具调用）
3. 不输出修复方案；确需给方向时标注【参考推测】并声明未经证据验证

### Phase 7：报告生成与用户最终确认

1. 按 [report-template.md](./report-template.md) 模板生成完整 Bug 报告并展示给用户；「最终确认结论」章节此时填入候选根因/建议方案 + 标注"待确认"
2. 用 AskUserQuestion 向用户确认两项，均允许自由填写补充（不限候选项）：
   - **最终根因**：列出 Phase 6 候选根因供选择；实际根因不在候选中时由用户直接填写（如"其实是配置漏了"）
   - **最终处理方案**：列出建议方案供选择；用户可采用自己的方案，或补充实际处理结果（如"数据已修，无需改代码"）
3. 用户回复后回填「最终确认结论」章节，更新本地 md 文件为终稿
4. 用户对报告其他内容有修正 → 一并修改后再次走确认环节

### Phase 8：知识库沉淀（三写）

用户确认终稿后依次执行：

1. **本地 md**：`{工程根目录}/docs/bug-reports/BUG-{yyyyMMdd}-{简述}.md`（默认当前工作区；出问题的工程非当前工作区时，先向用户确认报告归属工程）
2. **知识图谱**：create_entities 创建 BugReport 实体（observations 含最终确认结论）+ create_relations 关联 Service/Table 实体（详见 report-template.md）
3. **企业微信微盘**：通过 wecom-cli 上传报告终稿到团队微盘目标目录（默认 `系统资料/8质量管理/Bug知识库`，完整流程见 report-template.md 微盘沉淀规范）
4. 沉淀完成输出三处结果：md 文件路径、图谱实体名、微盘文件路径
5. 任一环节失败 → 按降级策略处理（跳过该环节并告知用户），不阻塞其余环节

## 阶段输出节奏

每个 Phase 结束输出该阶段结论摘要（事实集 / 调用链 / 证据表 / 假设验证表 / 根因 / 报告），再进入下一阶段；用户中途补充信息后，从受影响的阶段重新执行，已有效的结论不重复推导。
