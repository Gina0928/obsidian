# Monitor 问题定性与排查决策树

> **用途**：接到任何线上排查请求时，**先定性、再动手查**。本文件提供「问题分类 → 首查通道 → 下钻路径 → 横看佐证」的决策树，避免一上来就乱查日志。
>
> **配套**：具体查询模板见 [scenarios.md](./scenarios.md)，接口清单见 [endpoints.md](./endpoints.md)，查询示例见 [examples.md](./examples.md)。

---

## 一、总框架：四步递进

```
Step1 定性   从用户描述提取症状 → 确定问题类型 → 锁定首查通道
Step2 定位   用该通道查日志，提取目标对象（traceId/IP/连接数/线程数）
Step3 下钻   有 traceId 走精确串联；无 traceId 沿 IP 链近似串联，追到根因
Step4 验证   用系统状态 / 慢 SQL 反向确认（代码问题还是资源瓶颈）
```

> **关键铁律**：
> - **有 traceId 永远先走精确串联**（模板 1A），收敛最快
> - **traceId 缺失/不完善时不得放弃**，改走模板 1B（IP 链 + 业务标识近似串联）
> - **先排资源瓶颈再查代码**：很多"报错"本质是系统状态触发（如连接池耗尽导致超时）

## 二、问题定性决策树（症状 → 类型 → 模板）

```
用户描述的症状
│
├─ 提供了 traceId / 无明确报错、仅说"一次调用有问题"
│   └─ ▶ 调用链串联           → 模板 1（有 traceId 走 1A，无则走 1B）
│
├─ 接口报错 / 超时 / 依赖失败 / 服务调用失败
│   └─ ▶ Dubbo / Web 请求失败排查 → 模板 1 → 模板 2
│
├─ 页面卡顿 / 接口慢 / 操作响应慢
│   └─ ▶ 慢链路定位 → 模板 1 → 模板 3(慢 SQL) / 系统状态(资源)
│
├─ 具体提到"SQL 慢 / 数据库慢 / 某条查询慢"
│   └─ ▶ 慢 SQL 定位 → 模板 3（含 DB 慢 SQL 库 / 执行计划）
│
├─ MQ 消息丢失 / 消费失败 / 重复 / 想追一条消息去哪了
│   └─ ▶ Kafka 消息追溯 → 模板 4
│
├─ 前端 H5 / 小程序 / 页面报错
│   └─ ▶ 前端错误排查 → 模板 5（后端异常转模板 2）
│
├─ 系统级：OOM / 堆内存高 / CPU 飙升 / 线程池打满 / 连接数过高 / GC 频繁
│   └─ ▶ 系统状态诊断 → 模板 6
│
├─ 功能没人用 / 权限问题 / 某用户干了什么操作
│   └─ ▶ 操作日志聚合 → 模板 7
│
├─ 定时任务没跑 / 跑失败 / 调度异常
│   └─ ▶ XXL-Job 调度日志 → 模板 8
│
└─ 说不清楚 / 综合异常
    └─ ▶ 先按"报错信息 + 时间 + 用户/入口"做模板 1 串联起底，
       再从时间线中识别具体环节，回落到对应模板
```

## 三、问题类型 → 首查通道 → 判断依据 → 补充佐证（主表）

| 待排查问题 | 首查模板 | 关键判断字段 | 补充佐证（横看） |
|---|---|---|---|
| 单次调用链 | 模板 1 | `traceId` 或 `IP 链`+`user/uri/param` | elapsedTime 校验耗时构成 |
| 接口报错/超时/依赖失败 | 模板 2 | `status=fail/timeout` + `elapsedTime` | logger 找异常抛出处 |
| 接口/操作慢 | 模板 1 → 模板 3 | 耗时最大的环节 | 系统状态(模板6)看并发资源 |
| SQL 慢 | 模板 3 | `sort=elapsedTime` 找 Top | 执行计划 / 索引 / druid连接 |
| MQ 消息丢失/失败 | 模板 4 | `topic` + `key` + 消费组 | 必要时 reSendMq 补发 |
| 前端报错 | 模板 5 | 按 `url` 聚合 + 根因 | 后端 500 转模板 2 |
| 内存泄漏 / OOM | 模板 6 | `oldGenStr` 持续上涨不回落 | logger 的 GC/堆转储记录 |
| 异步导出/大批量任务堆打满（急性拥塞） | 模板 9 | 单 pod oldGen 分钟级骤升钉死 + Full GC 回收≈0 + sqlLog `returnRowCounts` 巨大或撞 pageSize 上限 | 模板 6 对照 pod + 历史同功能行数基线 |
| 线程池打满 | 模板 6 | `dubboUsed/dubboMax ≥80%` | 查下游慢调用(模板2) |
| 连接池耗尽 | 模板 6 | `druidActive ≥90%` | 慢 SQL Top(模板3) |
| CPU 飙升 | 模板 6 | `cpuUsage` 趋近 100% | logger 找死循环/热点 |
| 功能不生效/权限 | 模板 7 | user / function 聚合 | 操作日志明细 |
| 定时任务未跑 | 模板 8 | logId / 执行状态 | 调度器配置 |

## 四、典型排查路径（按场景走）

### 路径 A：在线的接口请求异常 / 报错
```
1. 报错含 traceId → 模板 1A 直接串联
   无 traceId → 模板 1B（user/uri/param + IP 链近似串联）
2. 命中 dubbo fail/timeout → 看 provider 端该接口 → 下钻 sql/logger
3. 系统状态(模板6)核验：抛错时段 heap 是否高位、druid 连接是否打满
```

### 路径 B：系统级资源问题（无明确请求对象）
```
1. 模板 6 系统状态诊断
   - Old Gen 持续上涨 → 内存泄漏 → dump + logger GC
   - dubbo 线程池 ≥80% → 下游慢/阻塞 → 查超时调用
   - druid 连接 ≥90% → 慢 SQL/未释放 → 查慢 SQL Top
   - CPU 趋近 100% → 死循环 → logger 找热点
2. 先按 pods 定位容器(alive/stopped)，再对具体 IP 查趋势
   纵向看该 IP 趋势 + 横向对比同应用其他实例
```

### 路径 C：链路性能恶化（变慢）
```
1. 模板 1 串联，找出耗时最大的环节（elapsedTime 对比）
2. 耗在 dubbo 调用 → 看 provider 端接口耗时 → 下钻 sql/logger
3. 耗在 SQL → 模板 3 慢 SQL + 执行计划
4. 耗在等待 → 系统状态看线程池/连接池是否打满
```

### 路径 D：间歇性偶发失败
```
1. 模板 2，定位 fail/timeout 集中时段
2. 对齐系统状态(模板6)：该时段是否 druid/dubbo 阈值告警、GC 停顿
3. 抽一个 traceId 走模板 1 完整复现现场（无 traceId 用 1B）
```

### 路径 E：消息/异步链路问题（Kafka）
```
1. 模板 4：按 topic/key 追溯消息轨迹
2. 结合消费组 consumers 判断是否被消费、投递到哪个服务
3. 消费端异常 → 转模板 1 (按该服务 IP) / 模板 2 (dubbo失败)
```

## 五、横切验证矩阵（下钻后反向佐证）

| 怀疑点 | 印证日志 | 印证指标 |
|---|---|---|
| 内存泄漏 | 系统状态(模板6) | oldGen 持续上涨不回落 |
| 线程池打满 | 系统状态 + dubbo | dubboUsed/dubboMax ≥80% |
| 连接池耗尽 | 系统状态 + 慢SQL | druidActive ≥90% 且慢SQL Top 高 |
| 下游服务慢 | dubbo | provider 端 elapsedTime 大 |
| SQL 未命中索引 | 慢 SQL + 执行计划 | 无索引走全表 |
| GC 停顿 | logger + 系统状态 | CPU 突刺 + oldGen 打满 |

## 六、判断优先级铁律

1. **有 traceId 永远走串联**——最快收敛，不猜。
2. **先排资源瓶颈再查代码**——很多报错是系统状态触发（连接池/线程池满），先排资源，避免在正常代码里找 bug。
3. **慢 ≠ 代码问题**——慢 SQL 优先于业务代码；线程池满优先于逻辑死循环。
4. **后端要对齐前端**——前端 500 根因大多在后端 logger/dubbo，不局限 webError。
5. **单实例 vs 全量**——系统状态按 IP 看，若仅某 pod 异常，优先 kill/扩容而非改代码。
6. **无 traceId 时标注置信度**——IP+业务标识=高、仅 IP+时间=中、仅应用+时间=低，不硬断言。

## 七、执行顺序（AI 受到排查请求时）

```
1. 读取本文件，对用户描述做【问题定性】（Step1），确定进入哪个模板
2. 若信息不足（无 traceId、无时间、无应用），先辅助性提问补齐关键项
   - 必补：大致时间（精确到小时）；可选：traceId / user / uri / 应用名
3. 按模板执行查询（Step2-3）
4. 输出时间线/结果时，用【横切验证】(第五部分)复核结论（Step4）
5. 对无 traceId 的近似结果，显式标注置信度与可复核方式
```
