# 实战案例：一PO多DO 要货单卡在初始化（测试环境，2026-09-10）

## 现象

物流 DO 单 `ASN999012609100005`（id=53235，asn_type=5 SCM / sub_type=501）已收货关单
（`asn_status=20`，已收 `12.000`）；其要货单 `ASN999012609100006`（id=53236，
asn_type=1 NORMAL / sub_type=103）仍为 `00 初始化`，已收 `0.000`，明细 57395/57398 均为 `00`。

状态更新入口（用户指定）：`com.jy.cl.wms.manager.in.biz.ReceiveBizService#updateSrcAsn`

## 定性过程

1. **DB 三件套**：头未动、明细未动，说明不是"部分成功"，要么没执行要么整体回滚。
2. **`async_msg_record`**：id=46242，`msg_type=4`，`business_id=53235`，
   `version=1 / del_flag=0` → **未消费成功**；同批其它单都是 `version=2 / del_flag=1`。
3. **日志**（monitor-test，`cl-wms-adapter-api-pre`，14:23:30–14:23:45，当天仅 1 条）：
   ```
   消息处理失败：RpcException: No provider available ... scm-scs
     com.jy.scm.scs.client.order.IOrderNoticeReceiveService
     → ReceiveBizService.callbackSCM(ReceiveBizService.java:2226)
     → AsyncAsnCallBackHandler.handle(AsyncAsnCallBackHandler.java:104)
     → KafkaMessageConsumer.hanldAsyncData(:136)
   ```
4. **源码**：`AsyncAsnCallBackHandler.handle()` 带 `@Transactional`，
   第 102 行 `updateSrcAsn()` 写状态，第 104 行 `callbackSCM()` 调 dubbo，**无 try/catch**。

→ 定性为 **B 型：写了但被回滚**。三条铁证（消息未消费 + 异常堆栈 + 同事务无 catch）全部命中。
`updateSrcAsn` 本身逻辑正常（实测能算出明细已收 12.000、单头应收 24.000/已收 12.000）。

## 为什么「一PO多DO」才暴露

`callbackSCM` 只在 DO 单状态已是 `20 已完成` 时才触发（`AsyncAsnCallBackHandler.java:103-105`）。
一PO多DO 场景下每个 DO 收完就关单 → 必然走到外部回写 → 一旦回写失败，
该 DO 对要货单的所有进度更新全部回滚；只要有一个 DO 卡住，要货单就长期停在初始化。
而 DO 只是部分收货（status=10）时反而不触发回写，`updateSrcAsn` 能正常提交——这是以前没暴露的原因。

## 结论与修复方向

- 修复：把 `callbackSCM` / `callbackPMS` 移出 `updateSrcAsn` 的事务边界
  （catch + 告警，或 `afterCommit` + 独立重试）。生产同样风险：scm-scs 抖动/超时会把要货单打回初始化。
- 补偿：`asyncMsgHandlerJob` 当天 0 条执行日志，积压未消费消息可追溯到 2026-05；
  scm-scs 恢复后对 id=46242 单条重跑即可补上（重跑前确认幂等，避免重复累加）。
- 环境：测试环境 `scm-scs`（IOrderNoticeReceiveService）、`jy-lot`（StkLotRpcService）当前均无 provider，
  属环境依赖缺失，非业务代码错误。

## 复盘要点（可迁移到其它单据）

- 状态没变 ≠ 逻辑没匹配上。先查**异步消息表**和**异常日志**，比读代码快得多。
- `async_msg_record` 的 `version/del_flag` 组合是判读消费结果的最快信号。
- 触发条件（"只有 status=20 才回写"）决定了问题在什么业务形态下暴露，是回答
  "为什么以前没问题" 的关键。
