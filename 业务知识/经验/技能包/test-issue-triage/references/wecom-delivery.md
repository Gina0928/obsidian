# 企业微信交付规范（结论优先，禁止思考过程）

本技能在企业微信（WeCom）通道下以「远程任务」方式被触发：用户发消息 → 助理在测试库
复现/验证 → 最终把结果经企业微信回传（如交付胡雨）。**企业微信里用户只能看到最终那
一条回复，看不到中间的思考、试错、工具调用与文档阅读过程**。因此最终消息必须是一份自洽
的「结论稿」，而不是工作笔记。

> **使用时机**：凡结果要经企业微信回传，一律先读本文件再写最终回复。
> 用户在会话里直接交互时，按 SKILL.md「Step 4 输出」正常展开，不套用本规范。

## 最终回复的三段式结构（移动端友好）

1. **一句话结论 / 判断**（最前面，让用户 3 秒内读懂结果）。测试环境结论要明确性质：
   「复现成功 / 复现失败 / 修复生效 / 未复现」或「差异定位到 X」。
2. **关键证据**（精简结构化表格，仅放能直接支撑结论的字段；金额与数量保留 Decimal
   精度，不四舍五入；口径有歧义时加一行注）。
3. **数据来源与口径**（明确标注「测试环境 jy_wms」＋门店 wh_id/时间区间/来源库/是否含
   日志交叉）＋ 可选的**下一步建议**（一句，给可执行动作）。

## 测试环境特有的标注义务（结论稿里必须带）

- **数据来源一律标「测试环境」**，不得与生成结论混写，避免收件人误当生产结论。
- **性能类结论必须标注「生产需复核」**：测试库数据量小、零数量行占比高，执行计划
  可能与生产完全不同，结论不得外推。示例：「该 SQL 在测试环境 EXPLAIN 走索引；
  **生产 700 万+ 行需复核执行计划**」。
- 若结论依赖数据量（如"零数量行占比高导致全表扫描"），显式提示「生产数据量为 X，
  需在生产复核」。
- 若结论涉及代码版本，标注依据的分支 / 提交，避免收件人误以为是已部署版本。

## 禁止带入企业微信最终回复的内容

- 思考过程 / 推理链条（"我怀疑是 X，于是去查 Y" 这类叙述）。
- SQL 原文堆砌、返回行数、`EXPLAIN` 全文、工具调用清单、`curl` URL。
- 文档阅读过程（"先读了 finishCount 优化文档……"）——结论里只保留文档支撑的要点。
- 中途试错、空查询、重试记录、内部状态回显。
- `traceId` 完整链路 / 异常堆栈全文（除非它是结论本身的核心证据，且已精简为要点）。
- 用于自我对齐的计划段落（如"本次计划：先 A 再 B"）。
- 源码拉取、git 命令、仓库路径等取证过程（结论里只保留「代码层面定位到 X 类 Y 方法」）。

## 未定位到根因 / 未复现时怎么回

直接写结论：「测试环境未复现（已确认测试库无该批数据 / 已排除 A·B）/ 复现成功但
根因待定」，并给建议的下一步（如"建议补充生产 traceId 或门店后在生产复核"）。
**不要发一长篇"我做了什么但没找到"**。

## 触发判定

- 用户在**本会话直接交互**（能看到工具过程）时，按 Step 4 正常展开。
- 凡结果要经**企业微信回传**（远程任务），一律套用本规范收敛为结论稿，无论排查
  过程多长、查了多少库。
