# 测试环境问题排查（jy_wms）

## 概述

面向测试环境 WMS 库（数据库名 `jy_wms`，与生产同名）的问题定位、复现与验证。
典型用途：复现生产反馈的问题、验证修复效果、确认 SQL 或代码改动的行为。

## 运行环境（固定，不随会话变化）

| 项 | 值 |
|---|---|
| 工作目录 | `D:\cl-wms`（所有文件读写、命令执行、代码检索均在此目录下进行） |
| 项目文档 | `D:\cl-wms\docs`（62 个 md，复现验证前必读相关文档，索引见 `references/docs-index.md`） |
| 模型 | `Hy4 preview`（本技能的所有推理与输出均使用此模型） |

工作目录是硬约束：即使用户消息里没提路径，或当前会话的工作区在别处，涉及
文件与代码的操作一律以 `D:\cl-wms` 为基准。

## 与生产的关键差异（先记住这几点）

1. **数据规模小**：测试库 492 张表，门店分表约 110 个，但单表行数远小于生产。
   生产 `stk_lot_loc`、`stk_minus` 量级在 700 万行以上，测试环境通常只有
   几千到几万行。
2. **零数量行占比高**：测试环境存在大量数量为 0 的记录，会导致执行计划与生产
   完全不同。
3. **性能结论不可外推**：在测试环境跑得快的 SQL，在生产可能全表扫描。
   **性能类问题必须在生产环境用 `EXPLAIN` 复核，不得只用测试结果下结论。**
4. **口径可能滞后**：测试库的表结构或字典数据可能落后于生产，核对前先比对结构。

## 执行流程

### Step 0：确认连接与门店

默认使用 `mcp__mysql_wms_test__query`。
`mcp__mysql_wms_testhw__query` 已失效（连接被拒），不要再尝试。

**MCP 连不上时（常见，启动阶段显示 "Still connecting"）走 db-cli 兜底**，不要卡住：

```bash
C:/Users/yuai/.workbuddy/binaries/python/envs/default/Scripts/python.exe \
  "C:/Users/yuai/.workbuddy/skills/db-cli/scripts/dbquery.py" test/jy_wms "SELECT ..." --format tsv
```

- 该 venv 已装 `pymysql` + `pyyaml`（`dbq` 包装脚本里的 shebang 是 macOS 路径，别直接跑）。
- 聚合查询或自带 LIMIT 时加 `--no-limit-check`，否则脚本会追加 `LIMIT 200` 导致语法错误。
- `DESC 表名` 会被追加 LIMIT 报错，改用 `information_schema.columns` 查列名。
- 连接信息唯一真源 `C:\Users\yuai\.workbuddy\skills\db-cli\config\connections.yaml`（`test-root` 库不限）。

门店不是必填项，但涉及门店分表时必须先确认分表存在：

```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_name = 'stk_trans_log_<wh_id>';
```

分表不存在时如实告知，不要用主表顶替。

### Step 1：查阅项目文档（复现前必做）

按 `references/docs-index.md` 的索引，读取 `D:\cl-wms\docs` 下与本次问题相关
的文档。测试环境排查通常要找两类：

1. **功能设计 / 修复文档** —— 确认「预期行为」到底是什么，否则在测试环境
   复现出来的现象无从判断对错。
   - 慢 SQL / 超时类：`docs\优化\` 下同名文档
   - 表用途与归档：`docs\需求与设计\` 下 `xxx用途与归档设计.md`
   - 业务流程：`docs\需求与设计\入库业务流程与数据表说明.md`、`加工详细设计方案.md`
   - 异步与事务：`docs\架构\项目异步处理机制手册.md`
2. **历史排查交接文档** —— 同类问题可能已经查过，`docs\优化\` 与
   `docs\测试\` 下的交接文档优先看。

要点：

- **不要全量读取**。目录共 62 个 md，按场景命中后再读。
- 文档头部有 `status`，**已废弃的跳过**；空文件（0 字节）读了没内容直接跳过。
- 文件名未命中时用 `Glob` 在 `D:\cl-wms\docs\**\*.md` 里按关键词搜。
- 读完后用一两句话说明读了哪些文档、关键结论是什么，再开始复现。

### Step 2：复现问题

1. 先明确要复现的现象与前置条件（门店、单据号、商品编码、时间范围）。
2. 测试环境查不到目标单据时，不要直接判定"问题不存在"，先确认测试数据里
   是否根本没有这批数据。
3. 涉及业务代码时，在 `D:\cl-wms` 下定位对应模块的实现（模块划分见
   `RULES.md`），把 SQL 与代码行为对照起来看；代码与文档描述不一致时显式指出。

### Step 3：定位与验证

- 不确定字段含义时先查 `information_schema.columns`，不凭记忆写 SQL。
- 需要验证修复效果时，明确写出「修改前行为 / 修改后行为」的对比。
- 涉及慢查询时在测试环境执行 `EXPLAIN`，但结论要标注「测试环境执行计划，
  生产需复核」。
- 若复现涉及报错链路，可先用日志接口拉取对应 traceId／时间区间的调用链（见下方「日志查询与交叉分析」），再回数据库对照数据。
- **需要看代码实现时**：默认按 `references/source-code-access.md` 走 git-cli 只读拉取
  到固定取证工作空间 `D:\workbuddy_file\git-repos\`，拉取前先向用户问清仓库与分支
  （品牌分支 yas/hmt/wky；映射表外的分支先 `git ls-remote --heads` 列出让用户选），
  再在副本内 Grep / Glob / Read。不以本地工作区代码作为取证来源，
  **版本没核对就别下"未复现"结论**。

### Step 4：输出

> 适用范围区分：下方条目适用于**对话内**完整输出（用户在本会话里直接交互、能看到
> 工具调用与中间过程时）。若结果需经**企业微信回传**（远程任务通道，用户只能看到
> 最终一条消息），一律套用末尾「企业微信交付规范」收敛为结论稿，不要把思考过程发过去。

- 结论先行：先给判断，再给证据。
- 开头交代本次读了 `docs` 下哪几份文档、关键结论是什么。
- 附可直接复核的 SQL 与返回行数。
- 明确标注数据来源为测试环境，避免与生产结论混淆。
- 若结论依赖数据量，显式提醒「生产数据量为 X，需在生产复核」。

### Step 5：复盘并记录反馈（收尾必做）

交付结论前花 10 秒自问两件事：「本轮有没有踩坑」「用户有没有纠正口径或结论」。
有就用 `scripts/feedback.py add` 记进共享反馈池，详见下方「自我改进回路」。

**判断标准只有一句：下次遇到同类任务，这条信息能不能让我少做一步？** 能就记，
不能就不写——凑数记录的条目会稀释反馈池，比不记更糟。

## 超时熔断（15 分钟无结论强制中断重启）

**目标：防止排查/复现陷入"循环自证"——反复用同类查询、同一假设空转，长时间给不出结论。**

### 计时

- 任务开始时记下起始时间（以会话 `current_time` 或第一条命令的 `date +%s` 为准）。
- 每完成一个阶段（约每 8-10 次工具调用）主动对表：跑一次 `date +%s` 与起始值比对，
  或用系统注入的当前时间估算。
- 判定条件：**累计超过 15 分钟且尚未形成可交付结论**（复现场景即"能否复现/修复是否生效"
  的明确判断）→ 立即触发熔断。不得以"就快了""再查一条"为由顺延。

### 用户主动中断（优先级最高，先于超时判定）

用户明确提出结束、中断、停止、不用继续查了、先到这里等意图时，**立即中止当前任务**：

1. 当下停掉手头的查询/命令，不再发起任何新的工具调用；
2. 不请求确认、不挽留、不用"马上就好"续跑；
3. 把当前进度收敛成一则简短小结输出：已确认事实、当前最优判断
   （复现成功/未复现/证据不足）、未完成的部分与卡点、如需继续可以从哪条线接着查；
4. 中断后不自动重启任务，等用户下一步指令。

**中断指令是全局的**：排查过程中若拉起过多个并行/后台任务（后台命令、子任务、
独立窗口/会话），收到中断指令时全部立即停止，不能只停当前窗口、留后台任务继续跑；
输出小结前先确认没有仍在运行的遗留任务（如仍在执行的取数命令）。

**任务隔离**：每次（重新）拉起一个排查/复现任务时新开一个独立窗口（会话），
一个窗口只跑一个任务，避免上下文互相污染；这样用户在任一窗口说"结束"时，
语义明确——该窗口任务即停，全局叫停则所有窗口一起停。

### 熔断动作（按序执行）

1. **立即停止当前查询线**：不再发起新的取数、日志拉取或源码检索。
2. **禁止循环自证**：同一假设连续 2 次验证失败即放弃该假设；不得再跑与已失败
   查询仅差个别字段的 SQL；"测试环境没数据"不能靠反复换表重查来回避。
3. **盘点已确认事实**：把已拿到的证据（含"排除了什么"）整理成 3-5 条。
4. **输出中断回复**：当前最优判断（复现成功/未复现/证据不足）+ 已确认证据 + 卡点 +
   拟换的路线，先让用户看到进展。
5. **重新拉起同一任务**：以新视角重启分析，且必须满足：
   - 先列「已排除路径」，新路线不得复用已证伪的查询或假设；
   - **换证据链**：原路线查库为主 → 改日志/源码为主（或反之）；原按单据追 →
     改按时间窗/商品/状态反查；
   - 重启前先核对测试环境部署版本与所拉分支是否一致（版本不符是"未复现"的常见假因）；
   - 重启后的分析同样受 15 分钟约束并重新计时。

### 二次熔断

重启后 15 分钟内仍无可交付结论 → **不再重启**，输出收尾包：

- 阶段性结论（现有证据能支撑的最大判断，明确标注哪些已验证、哪些是推测；
  性能类结论必带「生产需复核」）
- 明确卡点（缺什么数据/权限/版本信息/测试数据）
- 需要用户补充的具体信息清单

然后走 Step 5 复盘，把本轮熔断原因记入共享反馈池（kind 按反馈池分类表选择，
不带门店号/单据号/日期）。

### 熔断时禁止

- 为"找点东西"扩大查询范围（全表扫描、拉全量日志、全仓搜代码）。
- 把未验证的猜测包装成"已复现/未复现"结论。
- 静默继续跑原路线而不输出中断回复。
- 企业微信通道：中断回复与最终结论都按 `references/wecom-delivery.md` 收敛为结论稿。

## 日志查询与交叉分析

监控平台日志（见 `references/log-query.md`）在测试环境复现／验证时，与数据库是**互补的两条
证据链**。查询前务必先在 `references/log-query.md` 走「**问题定性 → 约束校验 → 日志类型路由**」
三步，再动手拉取；**复杂日志场景（Kafka 消息追溯、前端报错、操作日志聚合、写操作补发等）直接转
monitor-log 技能**取其完整模板与接口，本文件只覆盖 WMS 高频通道。日志结果应并入分析，而非只看一侧。

> **问题定性为「单据状态应该变但没变 / 变了又被打回」时，转 `async-callback-rollback` 技能**
> （异步回写失败导致事务回滚的排查定式，含 `async_msg_record` 消费结果判读与
> `@Transactional` 边界审计）。这类问题不要用本技能从零摸索。

### 构造与拉取
- 用 `scripts/build_log_url.py` 生成正确编码的 URL（重点：`executeTimeRange` 的
  `%3A` 与 `message` 多条件的 `+` 直连分隔符）。
- 优先 `curl` 下载到 `D:\cl-wms\logs\` 再 Read 分析；内部平台可能需登录态，失败则
  把 URL 交用户浏览器打开，或让用户把导出文件放到该目录。

### 日志 ↔ 数据库 双向交叉
- **日志 → 数据库**：用日志里的 traceId / 异常堆栈 / 出现的单据号·商品编码，回到
  测试库取数，确认数据侧是否也异常（例如日志报空指针，DB 里对应记录是否缺字段）。
- **数据库 → 日志**：测试库定位到异常单据／时间点后，用 `message` 关键字或时间区间
  去日志看完整调用链，确认现象发生的确切服务与报错，验证"复现成功"。
- 时间对齐到同一时区，用时间区间把"DB 的一条异常记录"和"日志的一段调用"对应起来。

### 输出时合并证据
- 同一份分析里同时给数据库证据与日志证据，例如「DB 中单据 DBxxxx 缺货明细为空
  （SQL 见上）；traceId=yyy 日志在 14:43:55 显示 AaaService 提前 return，未生成
  缺货记录」。
- 测试环境日志只反映测试行为，结论不得外推到生产；引用日志必标注环境与时间。
- 最终判断以"日志现象 + 测试库事实"相互印证，不单凭一侧下结论。

## 源码取证（默认走 git-cli，拉取前问分支）

三条证据链之一（数据库 / 日志 / 源码）。默认流程见 `references/source-code-access.md`：
先与用户确认仓库与分支，再用 git-cli 只读拉取到固定取证工作空间
`D:\workbuddy_file\git-repos\`，在副本内检索。不把本地开发工作区 `D:\cl-wms`
的代码当取证来源——测试环境部署的分支可能与本地不一致，复现判定前先核对版本。
跨系统调用（scm-scs、scm-wms、jy-dcs、jy-bltoise、qiulong）与其它品牌分支
（hmt-master / wky-master）都走 git-cli 技能的 `scripts/pull_source.py`。
只做读操作，禁止 push / commit，不在副本里改代码当修复或当复现环境。

## 改动测试数据的约定

默认只读。确需构造或修改测试数据（造单、改状态、清数据）时，必须先向用户
确认具体范围和影响，得到明确同意后再执行，并在执行后说明改了什么。

## 红线

- 不把测试环境的性能结论当成生产结论。
- 不在未确认的情况下修改数据。
- **不跳过文档直接复现**——先读 `D:\cl-wms\docs` 确认预期行为，否则无法判断
  测试环境跑出来的现象是对是错。
- 不假设测试库与生产库结构一致，跨环境比对时先核对 `information_schema`。
- 不脱离 `D:\cl-wms` 工作目录操作其它路径（用户显式指定除外）。

## 自我改进回路（反馈驱动）

每次任务收尾花 10 秒复盘：「本轮有没有踩坑」「用户有没有纠正口径或结论」。有就记进
共享反馈池（与另一排查技能共用），**先沉淀、再合并**：单次偶发事件不许改技能，同类
命中 ≥ 2 次或用户显式纠正才动 SKILL.md / references。

```bash
PY="C:/Users/yuai/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
$PY scripts/feedback.py add --skill test --kind env --topic "<通用规则，不带门店号/单据号/日期>" \
   --detail "<现象>" --fix "<怎么改>" --target "<落点文件>" --evidence "<报错/SQL/文档名>"
$PY scripts/feedback.py review        # READY 列：NOW 立即合并，WAIT 不许改
$PY scripts/feedback.py resolve F001 --to "references/environment.md"
```

`--topic` 写法、kind 分类表、合并落点决策树、反模式见 `references/feedback-playbook.md`。
`skill=both` 的条目必须同步改 `prod-issue-triage` 与 `test-issue-triage` 两侧。
