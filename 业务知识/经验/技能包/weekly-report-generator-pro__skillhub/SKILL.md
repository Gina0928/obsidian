# Weekly Report Generator — 周报生成器

Use when the user mentions 周报、写周报、生成周报、工作总结、weekly report、work summary, or asks to summarize weekly work. NOT for 日报、月报、年终总结、OKR制定.

## 描述

根据用户的每日工作记录或零散输入，自动生成结构化周报，突出工作成果和价值，告别流水账式周报，让汇报更专业、更高效。

## 重要限制（请提前告知用户）

- **需要工作素材**：无法凭空生成，需要用户提供本周工作内容（可以是零散记录）
- **不了解业务背景**：首次使用建议说明岗位和汇报对象，以便调整风格
- **数据需用户提供**：无法自动获取工时、代码提交等系统数据
- **不代替思考**：建议用户确认重点是否准确，避免遗漏重要工作

## 生成时机约束（仅本周结束后生成正式报告）

本技能的核心纪律：**正式周报只在本周（周一~周日）内容全部结束后才生成**，避免产出半成品周报。周内中途调用只产出清晰标注的【周中草稿】，不落盘正式报告。

- **目标周判定**：报告目标周由下方「闸门」步骤的脚本判定（周一出上周、其余出当前周），文件名 `weekly-{week_start}-{week_end}.md` 据此命名。
- **目标周与闸门**：
  - **周一**（任意时间）→ 目标周为**刚结束的上周**，视为已结束，出正式报告。
  - **周二 ~ 周日 22:00 前** → 目标周为**当前周**，视为周内，仅出【周中草稿】。
  - **周日 22:00 之后** → 目标周为当前周，视为已结束，出正式报告。
  - 一句话：仅"周一（出上周）"与"周日 22:00 后（出本周）"两种情形落盘正式报告，其余均为草稿。
- **为什么改**：原先自动化在周五触发，只覆盖周一~周五，漏掉周末、且周五晚间工作常未记录，周报不完整。现改为**每周一 07:00** 触发（见「自动化」配置），恰好越过闸门。

### 自定义区间（用户显式指定日期范围时）

用户可能不走自然周，而是直接指定区间（如"本周从 2026-09-20 到 2026-09-24"）。此时按以下规则处理，**不要硬套自然周闸门**：

1. **先核对星期**：把区间首尾日期换算成星期几，确认是否跨自然周边界（例：09-20 是周日、09-24 是周四 → 跨两周）。若跨边界，**必须先把核对结果告知用户并请其确认区间口径**，再动手——多数情况是笔误（想要的是整周）。
2. **用户确认采用自定义区间后**：
   - 文件名按用户给的区间命名：`weekly-{区间首日YYYYMMDD}-{区间末日YYYYMMDD}.md`；
   - `input/this-week-notes.md` 按区间的**实际天序**生成对应段落（如"周日 (09-20) / 周一 (09-21) … / 周四 (09-24)"），并在表头显式标注「自定义区间（非自然周）」+ 目标文件名，防止后续误判；
   - **完成度判定不套 `check_week.py`**（它按自然周 + 周日 22:00 后判定），改为"当前日期 > 区间末日"即视为周期结束、出正式报告；否则只出【周中草稿】；
   - YAML 的 `week_start` / `week_end` 填用户给的区间首尾日期，保持文件命名与元数据一致。
3. **区间结束后**照常执行「去重闸门」与 `.txt` 复制版流程；若用户中途要求出正式版，仍走「强制生成」分支（`generated_before_week_end: true`）。

```
用户：帮我写周报
→ 请提供本周的工作内容，可以是每日记录、完成的任务列表或零散笔记

→ 生成结构化周报，按项目/模块分类，突出成果

用户：帮我把周报写得更有亮点
→ 优化表达，量化成果，突出价值贡献

用户：老板喜欢简洁的风格
→ 调整为精简版，突出关键成果
```

## 能力

- 将零散工作记录整理成结构化周报
- 自动分类：按项目、按类型（开发/测试/会议等）
- 优化表达：将"做了XX"转化为"完成XX，实现XX效果"
- 量化成果：引导用户补充数据，让成果更有说服力
- 多种风格：详细版、精简版、汇报版
- 生成下周计划建议

## 执行步骤

### 闸门（必须最先执行）：周完成度校验

生成前先判定"本周是否已结束"，未结束绝不落盘正式报告。

1. 运行技能自带脚本获取判定（也可按上方"生成时机约束"用日期推算）：
   `python <skill_dir>/scripts/check_week.py`
   取输出中的 `is_complete`、`week_start`、`week_end`、`days_remaining`、`note`。
2. 若 `is_complete == true` → 进入 Step 1~4，正常生成并正式落盘 `weekly-{week_start}-{week_end}.md` 与同名 `.txt`。
3. 若 `is_complete == false` → **不生成正式报告、不落盘**：
   - 在对话中输出一份清晰标注 **【周中草稿 · 未完待续】** 的预览（基于已记录内容整理）。
   - 提示用户："`{note}`。可继续往 `input/this-week-notes.md` 补充；如需立即出正式版，回复"强制生成"。"
   - 除非用户明确"强制生成"，否则到此为止。
4. **"强制生成"分支**：忽略闸门，按当前已记录内容生成正式报告，并在 YAML 的 `generated_before_week_end` 置 `true`、正文顶部加一行"⚠️ 生成本周尚未结束，内容可能不完整"，提醒用户。

### Step 1: 收集信息
1. 询问用户岗位和汇报对象（首次使用）
2. 获取本周工作内容（任意格式均可）
3. 了解是否有特别想突出的成果

### Step 2: 内容整理
1. 识别并分类工作项（按项目/按类型）
2. 区分已完成和进行中的工作
3. 识别可量化的成果点

### Step 3: 优化表达
1. 将流水账转化为成果导向表达
2. 补充量化数据（如有）
3. 突出价值和影响

### Step 4: 生成周报
1. 按标准模板输出（含 YAML frontmatter 元数据，见下文）
2. 根据用户偏好调整风格
3. 提供下周计划建议（可选）
4. **落地主文件（默认行为）**：将报告写入固定绝对路径 `D:\workbuddy_file\weekly-pipeline\weekly-reports\weekly-{week_start}-{week_end}.md`（文件名由闸门判定的目标周决定，不随会话工作区变化）。文件名按周排序，便于自动化稳定读取。除非用户本次明确指定其他路径，否则一律落此目录。
5. **去重闸门（强制，不可跳过）**：对刚落盘的主文件执行 `python <skill_dir>/scripts/dedupe_report.py <主文件绝对路径> --fix`，按脚本输出的 `action` 处理重复项并重跑，**退出码为 0 且输出「未发现重复描述行」后才能进入下一步**。详见「去重规则」一节。
6. **同步生成复制版（默认行为）**：在同一目录再生成纯文本复制版 `weekly-YYYYMMDD-YYYYMMDD.txt`（同名不同后缀），按下方「复制版（.txt）规范」转换，供用户一键复制到企业微信 / 飞书 / 邮件 / Word 等任何平台。
7. **对话内附复制正文**：生成完成后，在对话末尾用代码块附上复制版全文（不含 frontmatter），并告知复制版文件路径，让用户直接复制代码块内容即可粘贴，无需再翻文件。若用户目标平台支持 Markdown（如飞书/Notion），也可提示从主文件 `## 本周工作总结` 起复制。
8. **生成后重置输入（仅 end-of-week 正式生成时执行）**：把 `input/this-week-notes.md` 的当前内容归档为 `weekly-reports/notes-{week_start}-{week_end}.md`（保留原始记录备查；文件名以 `notes-` 开头，不会被 `weekly-*.md` 通配误读），随后将 `input/this-week-notes.md` 重置为带表头引导的空模板（见下），供新一周记录。若用户要求保留累加内容，可跳过本步。

   重置用空模板：

   ````markdown
   # 本周工作记录（输入文件）

   > 这是「周报生成」自动化的**输入源**。平时随手往里记本周做了什么，每周一 07:00 自动化会读取本文件生成周报（仅本周结束后才生成）。
   > 格式不限：流水账、关键词、bullet 都行，周报生成器会帮你整理成结构化周报。
   > 若本文件为空或无实质内容，自动化会跳过生成并提醒你补充素材，**不会编造**。

   ---

   ## 周一
   -

   ## 周二
   -

   ## 周三
   -

   ## 周四
   -

   ## 周五
   -

   ## 周六/周日
   -

   ## 其他 / 待补充
   -
   ````

## 输出原则

1. **成果导向**：强调"完成了什么、带来什么价值"，而非"做了什么"
2. **量化优先**：有数据的成果更有说服力
3. **分类清晰**：按项目或工作类型组织，便于阅读
4. **突出重点**：重要成果放前面，用标记突出
5. **适度包装**：专业表达但不夸大
7. **零重复**：同一工作项、同一句话在全篇只允许出现一次；bullet 必须提供标题没有的增量信息，否则整行删除。落盘前由 `scripts/dedupe_report.py` 兜底校验，退出码非 0 不得交付。
8. **复制友好**：同一份周报提供双版本——Markdown 主文件（自动化/存档）+ 纯文本复制版（跨平台粘贴），默认同步生成，见「输出落地」一节。

## 去重规则（强制 · 落盘前必须跑脚本校验）

周报里**不允许出现重复描述行**。重复分四类，生成阶段按硬规则规避，落盘前用脚本兜底，双保险。

### 硬规则（生成时必须遵守）

1. **一条目最多 2 条 bullet，且 bullet 必须提供标题没有的增量信息。**
   增量信息只有以下五类，命中其一才允许写 bullet；**命中不了就只保留标题行，整条 bullet 删掉**：

   | 允许的增量类型 | 示例 |
   |----------------|------|
   | 量化数据（数字+单位，且该数字**未出现**在标题中） | `覆盖 6 张表，单表行数从 7.23M 降至 1.2M` |
   | 结论 / 根因 | `结论为 stk_minus_log 缺 wh_id 联合索引，补索引后 12s → 0.3s` |
   | 分天细节 | `08-03：自动分配归因未配置分配规则` |
   | 风险 / 影响描述 | `消除盘点阻塞风险，已对齐门店确认口径` |
   | umbrella 标题的子任务拆解 | 标题为「A + B + C」时，按 A / B / C 各写一行 |

   **明令禁止**：把标题换几个字重念一遍。对照：

   ```markdown
   ❌ 错误（bullet 纯复述标题，零增量 —— 整行删除）
   ✅ **拆分库存回写批次 JOB，改造消除 N+1 查询问题**（08-21）
   - 拆分库存回写批次 JOB，重构查询逻辑消除 N+1，性能改善

   ✅ 正确（只留标题行）
   ✅ **拆分库存回写批次 JOB，改造消除 N+1 查询问题**（08-21）

   ✅ 也正确（bullet 提供了标题没有的量化结果）
   ✅ **修复负库存日志慢 SQL**（09-01）
   - 结论为缺 wh_id 联合索引，补索引后查询 12s → 0.3s
   ```

2. **跨天合并同一工作项**：同一工作在多天反复记录（如"库存初始化""某接口自测"贯穿多日），合并为一条，日期标注合并区间（如 `08-31 ~ 09-01`），**不得按天拆成多条重复内容**。

3. **亮点不照抄正文**：`本周亮点` 只写价值、影响、量化结论，**禁止把正文条目扩写成亮点**。
   - ❌ 正文 `✅ 大表瘦身 JOB 全部开启，运行稳定（08-20）` → 亮点 `🌟 大表瘦身 JOB 全部开启并稳定运行：所有瘦身 JOB 投入常态化运行…`
   - ✅ 亮点 `🌟 大表瘦身落地，单表行数下降 83%，分区治理从方案进入生产阶段`

4. **下周计划的豁免边界**：计划承接 🔄 进行中工作、且写明下一步动作（收尾 / 上线 / 灰度 / 验证 / 观察 / 跟踪 / 复盘…）属正常承接，**不算重复**；只有把 ✅ 已完成条目原样搬进计划，或计划行没有任何下一步动作词，才算重复。

5. **相邻 / 同义条目合并**：内容高度相近或仅措辞不同的条目，合并为一条。

6. **归类后复查**：同一模块归类完成后，再通读一遍该模块，发现重复行立即合并。

### 落盘前闸门（必须执行，不可跳过）

主文件写盘后、生成 `.txt` 复制版之前，先跑检测脚本：

```bash
python <skill_dir>/scripts/dedupe_report.py <主文件绝对路径> --fix
```

- **自动清理**：L1 字面重复行、L3 高置信「bullet 复述标题」由脚本删除，原文件自动备份为 `<文件>.bak`。
- **人工处理**：脚本列出的「需人工处理」项，逐条按 `action` 执行——无增量的 bullet 整行删除、近似重复条目合并、照抄正文的亮点改写为价值陈述。
- **重跑到干净为止**：改完重跑脚本，**直到输出 `✅ 未发现重复描述行，可以落盘`、退出码为 0**，才继续生成 `.txt` 复制版。退出码非 0 一律不得进入下一步。
- 复制版由主文件转换而来，主文件已去重则复制版自动无重复，无需二次检测。

脚本检测的四类问题（阈值集中在脚本头部，可按实际语料微调）：

| 级别 | 问题 | 处理方式 |
|------|------|----------|
| L1 | 规范化后完全相同的行 | 自动保留首条、删除后续 |
| L2 | 跨条目 bigram 相似度 ≥ 0.70 | 人工合并为一条 |
| L3 | bullet 复述所属 ✅/🔄 标题（综合相似度 ≥ 0.55 自动删 / ≥ 0.30 提示） | 自动删或人工删整行 |
| L4 | 亮点 / 下周计划照抄正文条目（相似度 ≥ 0.50） | 人工改写 |

> 综合相似度 = 0.5×Jaccard + 0.3×标题被复述比例 + 0.2×bullet 照搬标题字数比例。
> bullet 若命中量化数字、结论/根因、分天细节、风险/影响任一豁免条件，则不判为复述。

## 输出落地（自动化友好 · 固定绝对路径）

> ⚠️ 重要：不要用会话工作区（如 `D:\workbuddy_file\2026-xx-xx-...`，每次对话都会换一个）作为输出目录。周报链路必须落在**固定的绝对路径**上，否则自动化会因目录变化而失效。

每次生成周报，除在对话中展示外，还会把**主文件（.md）+ 复制版（.txt）**写入固定目录：主文件供自动化脚本稳定读取，复制版供用户复制到其他平台：

- **根目录（固定，不随会话变化）**：`D:\workbuddy_file\weekly-pipeline\`
- **输入文件**：`D:\workbuddy_file\weekly-pipeline\input\this-week-notes.md` —— 用户平时往里记本周工作内容，自动化运行时读取它作为素材。若为空，自动化应跳过并提醒用户补充。
- **输出目录**：`D:\workbuddy_file\weekly-pipeline\weekly-reports\`
- **文件名**：`weekly-YYYYMMDD-YYYYMMDD.md`，两段分别为本周**周一**和**周日**日期（如 `weekly-20260803-20260809.md`）。文件名按字典序即时间序，自动化用 `weekly-reports\weekly-*.md` 通配后取末位即为最新一周。
- **格式**：主文件仅 Markdown（.md）；复制版为纯文本（.txt），见下节。
- **机器可读元数据**：每个文件顶部用 YAML frontmatter 写入结构化字段，供自动化解析（仍属 .md 文件，不影响人读）：

```yaml
---
title: 周报 | 张三 | 2026-08-03 ~ 2026-08-09
week_start: 2026-08-03
week_end: 2026-08-09
author: 张三
report_type: weekly
generated_at: 2026-08-09T22:00:00+08:00
generated_before_week_end: false   # 周中强制生成时置 true，提示内容可能不完整
---
```

正文沿用上方「输出格式」标准模板（从 `## 本周工作总结` 开始）。

### 复制版（.txt）规范

复制版与主文件**同步生成**（Step 4 第 5 点），用于把周报复制到不渲染 Markdown 的平台（企业微信、邮件、Word、微信等）。文件名为 `weekly-YYYYMMDD-YYYYMMDD.txt`，放在主文件同目录。转换规则：

1. **删除 YAML frontmatter**：以 `周报 | [姓名] | [日期范围]` 开头（一行），不带 `---`。
2. **删除 emoji**：去掉 ✅ / 🔄 / 🌟 / ⚠️ / 📊 等所有 emoji 图标，保留文字本身。
3. **删除 Markdown 符号**：去掉 `**加粗**`、`*斜体*`、`` `行内代码` ``、`>` 引用、`---` 分隔线、`━━━━` 装饰线；`#` 标题全部转纯文本。
4. **标题层级转纯文本**：`## 本周工作总结` → `【本周工作总结】`；`### 一、xxx` → `一、xxx`；`## 本周亮点` → `【本周亮点】`，其余段落标题（遇到的问题 / 下周计划）同理。
5. **列表保留**：`- ` 和 `1. ` 数字列表原样保留（各平台显示正常）；删除 Markdown 语法造成的多余缩进。
6. **空行分隔**：各章节、各项目块之间保留一个空行，避免粘贴后挤成一团。
7. **其余正文（含日期标注、括号说明）原样保留**，与主文件内容一致。

示例（节选）：

```
周报 | 张三 | 2026-08-03 ~ 2026-08-09

【本周工作总结】

一、WMS 大表瘦身（已上线）
- 大表瘦身 JOB 自测并上线（08-17）
- 归档表迁移至归档库，测试并上线（08-18）

【本周亮点】
- 大表瘦身 JOB 全部开启并稳定运行

【遇到的问题】
本周暂无

【下周计划】
1. 继续跟进剩余门店库存初始化
```

生成复制版后，在对话末尾以代码块展示其全文，方便用户直接复制。

**自动化读取建议**
- 取最新一周：`ls D:\workbuddy_file\weekly-pipeline\weekly-reports\weekly-*.md` → 按文件名排序 → 末位。
- 解析元数据：读取文件顶部 `---` 包裹的 YAML（任意 YAML 库或简单正则均可）。
- 正文段落稳定包含：本周工作总结 / 本周亮点 / 遇到的问题 / 下周计划。
- 复制版 `.txt` 与主文件 `.md` 同名不同后缀，`weekly-*.md` 通配不会匹配到 `.txt`，不影响自动化取数。

**迁移注意**：如需把 `weekly-pipeline` 移到别处，须同步修改本节路径、自动化 `cwds` 与 prompt 中的路径，保持三处一致。

## 错误处理

| 异常场景 | 提示语 |
|----------|--------|
| 用户未提供工作内容 | "📝 请提供本周的工作内容，可以是：1) 每日简单记录 2) 完成的任务列表 3) 零散的工作笔记" |
| 内容过于简略 | "💬 信息较少，我先生成一版。建议补充：具体做了什么、花了多少时间、有什么成果" |
| 全是会议没有产出 | "📅 本周会议较多，建议补充：会议产出了什么结论或推动了什么进展" |
| 无法判断优先级 | "🤔 这些工作中，哪个是本周最重要的成果？我来重点突出" |
| 工作内容重复 | "🔄 发现 N 处重复描述行，已按去重规则合并/删除（详见检测脚本输出），请确认是否准确" —— 先跑 `dedupe_report.py --fix` 再回复，不要口头承诺去重却没执行 |

## 常见问题（FAQ）

**Q: 我的工作记录很乱，能整理吗？**
A: 可以。随便粘贴过来，我会帮你分类整理成结构化周报。

**Q: 怎么让周报更有亮点？**
A: 提供具体数据（如处理了多少、提升了多少），我会帮你包装成亮点。

**Q: 可以生成不同风格吗？**
A: 可以。告诉我你的汇报对象偏好（详细/简洁/数据导向），我来调整。

**Q: 下周计划怎么写？**
A: 可以根据本周进行中的工作自动生成，或者你告诉我下周重点，我来补充。

**Q: 能帮我美化格式吗？**
A: 可以。每次生成周报都会**同步产出双版本**：Markdown 主文件（适合飞书/Notion）和纯文本复制版 .txt（无 emoji、无 Markdown 符号，适合企业微信/邮件/Word，直接全选复制即可）。

**Q: 复制到企业微信/邮件后格式乱了怎么办？**
A: 用复制版 .txt，不要复制主文件。复制版已去掉 YAML 头、emoji 和 Markdown 符号，纯文本粘贴到任何平台都不会乱；也可以直接复制对话末尾代码块里的正文。

**Q: 每周都要重新说明岗位吗？**
A: 不用，首次说明后我会记住风格偏好。

## 最佳实践

1. **日常积累**：每天花1分钟记录完成的工作，周末整理更轻松
2. **量化习惯**：随手记录数据（处理量、耗时、提升比例）
3. **突出价值**：思考"这个工作对团队/业务有什么帮助"
4. **适配对象**：给技术leader写技术细节，给业务leader写业务价值
5. **保持一致**：固定周报格式，便于追踪和对比

## 不适用场景

| 场景 | 原因 | 替代方案 |
|------|------|----------|
| 日报生成 | 格式和侧重点不同 | 调整为日报模式 |
| 月报/季报 | 需要更宏观的总结视角 | 使用月报生成工具 |
| 年终总结 | 需要全年回顾和规划 | 使用年终总结模板 |
| OKR制定 | 不是周报范畴 | 使用OKR工具 |

### 常见误用

- **误用 1**：不提供任何内容就要求生成 → 需要提供工作素材
- **误用 2**：期望自动获取代码提交记录 → 需要手动提供或粘贴
- **误用 3**：要求编造没做过的工作 → 只能基于真实工作优化表达

## 安全与隐私

- 周报文件按用户要求写入本地工作区的 `weekly-reports/` 目录（用户自有环境，用于自动化读取），不会上传或分享给第三方
- 建议脱敏处理敏感项目名称或客户信息后再落盘
- 生成内容仅返回给用户，不会对外分享
