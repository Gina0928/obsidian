# 生产环境问题排查与报表拉取（jy_wms）

## 概述

面向生产环境 WMS 库（数据库名 `jy_wms`）的问题定位与数据提取。覆盖两类诉求：
一是排查某个门店的异常（库存对不上、单据未分配、初始化差异等），二是按门店
拉取数据并生成报表。所有操作只读，不写生产库。

## 运行环境（固定，不随会话变化）

| 项 | 值 |
|---|---|
| 工作目录 | `D:\cl-wms`（所有文件读写、命令执行、代码检索均在此目录下进行） |
| 项目文档 | `D:\cl-wms\docs`（62 个 md，排查前必读相关文档，索引见 `references/docs-index.md`） |
| 模型 | `Hy4 preview`（本技能的所有推理与输出均使用此模型） |

工作目录是硬约束：即使用户消息里没提路径，或当前会话的工作区在别处，涉及
文件与代码的操作一律以 `D:\cl-wms` 为基准。项目内另有 `RULES.md`（开发规范）
与 `claude.md`（项目对 AI 的约定），动手前先看。

## 硬约束（优先级高于一切流程）

1. **先读文档再查库**：执行任何 SQL 前，必须先按 `references/docs-index.md`
   定位并读取 `D:\cl-wms\docs` 下的相关文档。文档里有结论的，以文档为起点，
   再用数据库实测验证，不要从零猜表结构和业务逻辑。
2. **门店必填**：任何查询执行前必须已确定门店。未确定时先追问，不得跳过。
3. **只读**：只允许 `SELECT`／`SHOW`／`DESCRIBE`。禁止 `UPDATE`／`DELETE`／
   `INSERT`／`DDL`。定位结论以证据呈现，不擅自"修复"数据。
4. **精度**：金额与数量一律用 Decimal 处理，禁止浮点数中间运算，避免精度丢失。

## 执行流程

### Step 0：确认门店（未通过则不得继续）

按以下顺序判定：

1. 用户给出 4 位数字编码（如 `1607`、`1285`）→ 直接作为 wh_id 使用。
2. 用户给出门店名称或简称（如「沙市七中」「面包加工厂」）→ 查 `md_warehouse`
   解析出编码：

   ```sql
   SELECT warehouse_code, warehouse_name, store_id
   FROM md_warehouse
   WHERE warehouse_name LIKE CONCAT('%', '<门店名>', '%')
      OR warehouse_short_name LIKE CONCAT('%', '<门店名>', '%')
   LIMIT 20;
   ```

3. 命中多条 → 列出「编码 + 门店名 + 所属城市」让用户确认，不得自行挑选。
4. 未命中或用户完全没提门店 → 只输出一句追问，例如：
   「请提供要查的门店（wh_id 或门店名称都可以），生产环境查询需要按门店定位。」
   然后停止，不做任何查询。

确定门店后，回显一行确认供用户核对：
`已定位门店：1607（沙市七中）`

若本步因缺少门店而中止，**不要空等**：在同一次回复里追问门店的同时，先执行
Step 1 读文档（读文档不依赖门店），避免白等一轮。

### Step 1：查阅项目文档（查库前必做）

按 `references/docs-index.md` 的索引，定位并读取 `D:\cl-wms\docs` 下与本次
问题相关的文档。要点：

- **不要全量读取**。目录共 62 个 md，最大 50KB+，按场景命中后再读。
- 文件名未命中时，用 `Glob` 在 `D:\cl-wms\docs\**\*.md` 里按关键词搜文件名。
- 文档头部有 `status`（`草案` / `已定稿` / `已废弃`），**已废弃的跳过**。
- 空文件（如 `StkMinusManager.findMinusPage慢SQL诊断与优化方案_2026-08-05.md`
  为 0 字节）读到空内容直接跳过，换同主题的其它版本。

典型路由（完整表见索引文件）：

| 问题类型 | 读哪里 |
|---|---|
| 慢 SQL / 接口超时 | `docs\优化\` 下同名文档（如 `finishCount超时接口优化交接文档.md`） |
| 某张表是干什么的、怎么归档 | `docs\需求与设计\` 下 `xxx用途与归档设计.md` |
| 库存六表分区 | `docs\需求与设计\库存六表wh_id分区_DTS*.md` |
| 入库 / 加工 / 收货业务流程 | `docs\需求与设计\入库业务流程与数据表说明.md`、`加工详细设计方案.md`、`asn\` |
| 异步事件、事务回滚 | `docs\架构\项目异步处理机制手册.md` |
| 大表诊断与收敛 | `docs\大表优化诊断报告_2026-08-05.md`、`大表收敛方案_2026-08-05.md` |
| 门店初始化差异 | `docs\部署运维\新增商户门店信息初始化指南.md` |

读完后用一两句话说明「读了哪份文档、其中的关键结论是什么」，再进入查库。
文档结论与数据库实测冲突时，**以实测为准**并显式指出差异。

### Step 2：选择数据库连接

| 场景 | 工具 |
|---|---|
| 默认生产主库（门店分表最全，110+ 个） | `mcp__mysql_wms_yas_prod__query` |
| 用户明确提到 wky 那套生产 | `mcp__mysql_wms_wky_prod__query` |
| 商品主数据（ty） | `mcp__mysql_ty_yas_product_prod__query` |
| 商品主数据（zq） | `mcp__mysql_zq_yas_product_prod__query` |

未指定时默认走主库。若 MCP 连接不可用，改用 Python + pymysql 兜底，
连接参数从既有配置中获取，不要求用户重复提供。

### Step 3：路由门店分表

库存流水按门店分表，表名规则为 `stk_trans_log_{wh_id}`，例如门店 1607 对应
`stk_trans_log_1607`。查流水前先确认该分表存在：

```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_name = 'stk_trans_log_<wh_id>';
```

分表不存在时如实告知，不要退回查主表 `stk_trans_log`（结构与口径都不同）。

### Step 4：定位问题

先读 `references/environment.md` 确认涉及的表与字段，再按场景取数。
不确定表结构时先 `DESCRIBE` 或查 `information_schema.columns`，不凭记忆写 SQL。

常见场景与入口表：

| 场景 | 主要入口 |
|---|---|
| 库存数量／金额对不上 | `stk_sku`、`stk_sku_lot`、`stk_lot_att`、`stk_lot_loc` |
| 库存初始化差异 | `stk_init_header` → `stk_init_detail` → `stk_init_out_log` |
| 调拨单未自动分配／缺货 | `doc_alc_header`、`doc_alc_detail`、`doc_do_lack_detail` |
| 出库单状态异常 | `doc_do_header`、`doc_do_detail` |
| 收货／入库异常 | `asn_header`、`asn_detail` |
| 一段时间内的库存变动 | `stk_trans_log_{wh_id}` |

排查原则：
- 先锁定单据或商品，再展开明细，避免上来就全表扫描。
- 每个结论都要附上可直接复核的 SQL 与返回行数。
- 多步查询按「先查 A 拿到 id，再用 id 查 B」的顺序执行，不要假设 id。
- 若手头有 traceId 或报错关键字，可先用日志接口拉取调用链（见下方「日志查询与交叉分析」），再回数据库按日志里出现的单据号／商品编码取数。
- **需要看代码实现时**：默认按 `references/source-code-access.md` 走 git-cli 只读拉取
  到固定取证工作空间 `D:\workbuddy_file\git-repos\`，拉取前先向用户问清仓库与分支
  （品牌分支 yas/hmt/wky；映射表外的分支先 `git ls-remote --heads` 列出让用户选），
  再在副本内 Grep / Glob / Read。不以本地工作区代码作为取证来源，
  禁止用本地代码硬套生产行为。

### Step 5：生成报表

1. 明确报表的行维度（门店／商品／单据／日期）与指标口径。
2. 时间范围缺省时默认当天，并在输出中注明。
3. 结果导出为 `.xlsx` 时：一个 sheet 明细、一个 sheet 汇总；表头用中文。
4. 报表首行标注生成时间、门店、数据区间、数据来源库。

### Step 6：复盘并记录反馈（收尾必做）

交付结论前花 10 秒自问两件事：「本轮有没有踩坑」「用户有没有纠正口径或结论」。
有就用 `scripts/feedback.py add` 记进共享反馈池，详见下方「自我改进回路」。

**判断标准只有一句：下次遇到同类任务，这条信息能不能让我少做一步？** 能就记，
不能就不写——凑数记录的条目会稀释反馈池，比不记更糟。

## 超时熔断（15 分钟无结论强制中断重启）

**目标：防止排查陷入"循环自证"——反复用同类查询、同一假设空转，长时间给不出结论。**

### 计时

- 任务开始时记下起始时间（以会话 `current_time` 或第一条命令的 `date +%s` 为准）。
- 每完成一个阶段（约每 8-10 次工具调用）主动对表：跑一次 `date +%s` 与起始值比对，
  或用系统注入的当前时间估算。
- 判定条件：**累计超过 15 分钟且尚未形成可交付结论** → 立即触发熔断。
  不得以"就快了""再查一条"为由顺延。

### 用户主动中断（优先级最高，先于超时判定）

用户明确提出结束、中断、停止、不用继续查了、先到这里等意图时，**立即中止当前任务**：

1. 当下停掉手头的查询/命令，不再发起任何新的工具调用；
2. 不请求确认、不挽留、不用"马上就好"续跑；
3. 把当前进度收敛成一则简短小结输出：已确认事实、当前最优判断、
   未完成的部分与卡点、如需继续可以从哪条线接着查；
4. 中断后不自动重启任务，等用户下一步指令。

**中断指令是全局的**：排查过程中若拉起过多个并行/后台任务（后台命令、子任务、
独立窗口/会话），收到中断指令时全部立即停止，不能只停当前窗口、留后台任务继续跑；
输出小结前先确认没有仍在运行的遗留任务（如仍在执行的取数命令）。

**任务隔离**：每次（重新）拉起一个排查/复现任务时新开一个独立窗口（会话），
一个窗口只跑一个任务，避免上下文互相污染；这样用户在任一窗口说"结束"时，
语义明确——该窗口任务即停，全局叫停则所有窗口一起停。

### 熔断动作（按序执行）

1. **立即停止当前查询线**：不再发起新的取数、日志拉取或源码检索。
2. **禁止循环自证**：同一假设连续 2 次验证失败即放弃该假设；不得再跑与已失败
   查询仅差个别字段的 SQL。
3. **盘点已确认事实**：把已拿到的证据（含"排除了什么"）整理成 3-5 条。
4. **输出中断回复**：当前最优判断 + 已确认证据 + 卡点 + 拟换的路线，先让用户看到进展。
5. **重新拉起同一任务**：以新视角重启分析，且必须满足：
   - 先列「已排除路径」，新路线不得复用已证伪的查询或假设；
   - **换证据链**：原路线查库为主 → 改日志/源码为主（或反之）；原按单据追 →
     改按时间窗/商品/状态反查；
   - 重启后的分析同样受 15 分钟约束并重新计时。

### 二次熔断

重启后 15 分钟内仍无可交付结论 → **不再重启**，输出收尾包：

- 阶段性结论（现有证据能支撑的最大判断，明确标注哪些已验证、哪些是推测）
- 明确卡点（缺什么数据/权限/版本信息）
- 需要用户补充的具体信息清单

然后走 Step 6 复盘，把本轮熔断原因记入共享反馈池（kind 按反馈池分类表选择，
不带门店号/单据号/日期）。

### 熔断时禁止

- 为"找点东西"扩大查询范围（全表扫描、拉全量日志、全仓搜代码）。
- 把未验证的猜测包装成结论。
- 静默继续跑原路线而不输出中断回复。
- 企业微信通道：中断回复与最终结论都按 `references/wecom-delivery.md` 收敛为结论稿。

## 日志查询与交叉分析

监控平台日志是与数据库**同等地位**的排查输入（接口构造、字段、路由见
`references/log-query.md`）。拉取前先走该文件的「问题定性 → 约束校验 → 日志类型路由」三步。

- **复杂日志场景**（Kafka 消息追溯、前端报错、操作日志聚合、写操作补发）直接转 `monitor-log` 技能。
- **「单据状态应该变但没变 / 变了又被打回」** 直接转 `async-callback-rollback` 技能。
- 用 `scripts/build_log_url.py` 生成 URL（注意 `executeTimeRange` 的 `%3A` 与 `message`
  的 `+` 分隔符），`curl` 下载到 `D:\cl-wms\logs\` 再分析；需登录态则把 URL 交用户浏览器打开。

**双向交叉**：日志拿到 traceId / 单据号 → 回库取明细；库里定位到异常单据或时间点 →
用关键字或时间区间去日志查调用链。两侧时间对齐同一时区；结论必须「日志现象 + 数据库事实」
互相支撑，并标注日志来源环境与时间。

## 源码取证（默认走 git-cli，拉取前问分支）

三条证据链之一（数据库 / 日志 / 源码）。默认流程见 `references/source-code-access.md`：
先与用户确认仓库与分支，再用 git-cli 只读拉取到固定取证工作空间
`D:\workbuddy_file\git-repos\`，在副本内检索。不把本地开发工作区 `D:\cl-wms`
的代码当取证来源——线上部署版本可能与本地不一致。跨系统调用（scm-scs、
scm-wms、jy-dcs、jy-bltoise、qiulong）与其它品牌分支（hmt-master / wky-master）
都走 git-cli 技能的 `scripts/pull_source.py`。只做读操作，禁止 push / commit，
不在副本里改代码当修复。

## 输出规范

> 适用范围区分：下方条目适用于**对话内**完整输出（用户在本会话里直接交互、能看到
> 工具调用与中间过程时）。若结果需经**企业微信回传**（远程任务通道，用户只能看到
> 最终一条消息），一律套用末尾「企业微信交付规范」收敛为结论稿，不要把思考过程发过去。

- 结论先行：先给判断，再给证据。
- 开头交代背景依据：本次读了 `docs` 下哪几份文档、关键结论是什么。
- 数据用结构化表格呈现，字段含义用中文表头，含义有歧义时加注说明。
- 金额与数量保留原始精度，不四舍五入到整数；必要时同时给出合计。
- 明确写出「数据来源：生产 jy_wms，门店 X，时间区间 Y」。
- 未查到数据时不静默返回空结果，说明查了什么、为什么为空。

## 红线

- 不写生产库，不做任何数据修正。
- 不在未确认门店的情况下跑查询。
- **不跳过文档直接写 SQL**——`D:\cl-wms\docs` 里已有的结论必须先读。
- 不用模糊猜测的表名或字段名，不确定就先查 `information_schema`。
- 不把测试环境的结论当成生产结论，反之亦然。
